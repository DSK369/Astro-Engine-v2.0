# Plan 6 — Integrate KP Horary and Gochara Transit

**Status of this plan:** original, authored for this project — not pasted from an external
source like Plans 1–3. Unlike Plans 4 and 5 (new calculation work), this plan is **pure
integration**: both features described below already exist, are already working, and were
simply never merged into the GitHub `astro-engine` repo this project's active development
happens in. That makes this the lowest-risk, fastest-to-ship plan of the three written this
round — see this plan folder's README, "Suggested order of work."

---

## 1. What already exists

### 1.1 KP Horary (Prasna) — `astro-engine-v2/core/horary.py`

A complete implementation, not a stub:

- **`core/data/kp_horary_249.py`** — the 249 KP horary sub-lord divisions, covering 0–360°
  with no gaps or overlaps, auto-generated by `tools/gen_kp_horary_table.py` from first
  principles (each of the 27 nakshatras split among the 9 Vimshottari lords in proportion to
  their dasha years, further split at rashi boundaries). Its header comment records that this
  table was **cross-validated against two independent, unrelated implementations**
  (VedicAstro's `KP_SL_Divisions.csv` and PyJHora's `prasna_kp_249_dict`, both of which are
  now also available locally under `research/`) — 245/249 rows agree to sub-arcsecond
  precision; the remaining 4 (rows 171–172, 201–202) use a documented, deliberate correction
  matching both external sources at a boundary where the pure fraction-of-120 calculation
  differs by exactly 20 arcminutes from a known historical rounding in the original printed
  KP ready-reckoner tables.
- **`core/horary.py`** — `get_horary_range(n)` (row lookup), `get_kp_number_for_longitude(lon)`
  (reverse lookup), and `find_exact_ascendant_time(date, tz, lat, lon, horary_number)`: an
  adaptive-step search (coarse when far from the target zone, down to 0.05s steps near
  convergence) for the moment on a given date the Ascendant enters the target horary number's
  zone, then builds a full Lagna at that moment. It self-verifies — asserts the resulting
  Lagna's sub-lord matches the target row's sub-lord, catching exactly the kind of
  ayanamsa-mismatch bug this project has now found and fixed twice (this plan folder's
  README; Plan 4 §3.1).
- **`services/app.py: POST /horary`** — takes a date + location + horary number 1–249, finds
  the matching moment, and runs it through the **exact same downstream pipeline** as
  `POST /chart` (planets, houses, cusps, significators, ruling planets) — a horary chart and
  a natal chart differ only in how the "birth" moment was chosen, not in any subsequent
  calculation.

This directly answers Plan 2 §20 ("KP has a powerful Horary system... a KP Horary number is
traditionally selected within a prescribed range, and a chart is constructed for the
question") — which this plan folder's README had listed as "not yet built" before this
snapshot was found.

### 1.2 Gochara (transit visualizer) — `github.com/DSK369/Astro-Engine-Gochar`

Confirmed via `git remote -v` on the local working copy
(`Project_v2/Project/gochara/`) that this is a real, separate GitHub repo, not a
loose folder. A complete, documented, standalone application:

- **`backend/`** — FastAPI. `POST /api/ephemeris` takes a time range (up to 45 years),
  timezone, and calculation settings, samples up to 3000 points, and returns per-planet
  sidereal-longitude time series plus retrograde flags. `GET /api/meta` lists supported
  planets/ayanamsa modes/limits.
- **`frontend/`** — dependency-free static HTML/canvas (no build step). Zoomable/pannable
  timeline, Rashi/Nakshatra/Nakshatra-Charan Y-axis granularity, bilingual (EN/हिंदी) band
  labels, calendar gridlines, always-on crosshair, dashed retrograde rendering. Served from
  the same FastAPI process as the API — one port, no separate dev server.
- Explicitly designed as an `astro-engine` sibling: it points at `../astro-engine/ephemeris`
  for Swiss Ephemeris data (avoiding a duplicate ~100MB+ download) and falls back to
  swisseph's built-in Moshier model if that path isn't found.

This directly answers Plan 2 §24 ("Transit... not yet built") — also previously listed as a
gap in this plan folder's README before the repo was found.

## 2. Accuracy check — one of these needs the fix from this session, one doesn't

Before planning the merge mechanically, both were checked against the ayanamsa/offset bug
documented in this plan folder's README (the `-0.1°` offset + 2-arg `set_sid_mode` +
`FLG_SIDEREAL`/`SIDM_USER` precession-drift bugs found and fixed in the GitHub `astro-engine`
repo this session):

- **`astro-engine-v2/core/horary.py` — has the bug.** Its `_fast_ascendant_longitude()`
  helper hard-codes `AYAN_OFFSET = -0.1` (comment: "SAME OFFSET as houses.py / planets.py /
  cusps.py, kept consistent"), and `find_exact_ascendant_time()` calls
  `core.houses.calculate_lagna(jd, latitude, longitude)` — the **old**, pre-fix 3-argument
  signature (no explicit `ayanamsa_value` parameter) that this session changed to a 4-argument
  signature accepting the ayanamsa value explicitly. Porting `horary.py` into the current
  (fixed) `astro-engine` therefore isn't a drop-in file copy — it needs updating to the new
  `calculate_lagna(jd, lat, lon, ayanamsa_value)` signature and to drop `AYAN_OFFSET` from its
  own search loop, exactly the same change already made to `core/houses.py`,
  `core/planets.py`, and `core/cusps.py`. The 249-number table itself (§1.1) is **unaffected**
  — it's pure proportional zodiacal math (nakshatra spans divided by dasha-year ratios), not
  tied to any ayanamsa or tropical/sidereal conversion, so nothing about *it* needs to change.
- **`Astro-Engine-Gochar/backend/ayanamsa.py` and `ephemeris.py` — already correct.**
  Independently checked (not assumed from the README's claim of "same approach"): both files
  already use the 3-argument `swe.set_sid_mode(swe.SIDM_USER, 0, value)` call and compute
  tropical longitude with manual ayanamsa subtraction (`FLG_SWIEPH | FLG_SPEED`, no
  `FLG_SIDEREAL`) — the exact pattern this session's fix applied to the main engine. Both
  files' own comments cite the precession-drift pitfall by name. Gochara needs **no accuracy
  changes** — only the process/deployment integration in §4.

## 3. Merging KP Horary

1. **Copy `core/horary.py` and `core/data/kp_horary_249.py`** from `astro-engine-v2` into the
   current `astro-engine`'s `core/` (creating `core/data/` if it doesn't exist — check for a
   package `__init__.py` there, `astro-engine-v2` has one).
2. **Update the ported `horary.py`** to match the current `core/houses.py`:
   - Remove `AYAN_OFFSET = -0.1`.
   - Change `_fast_ascendant_longitude(jd, latitude, longitude)` to accept an explicit
     `ayanamsa_value` parameter and subtract it directly (mirroring `core/houses.py`'s
     `calculate_lagna`), instead of calling `swe.get_ayanamsa(jd)` internally.
   - Update `find_exact_ascendant_time()`'s call to `calculate_lagna(...)` to pass the
     ayanamsa value through (matching the 4-argument signature `core/houses.py` now has),
     and thread that same parameter into `find_exact_ascendant_time()`'s own signature so the
     caller (the new `/horary` endpoint, next) supplies it exactly once, the same pattern
     `services/app.py: post_chart()` already establishes for `/chart`.
3. **Add `POST /horary` to `services/app.py`**, following `post_horary()`'s existing logic
   (§1.1) but calling the current (fixed, and since this session, also-extended)
   `core/planets.py: get_all_planets()`, `core/cusps.py: calculate_placidus_cusps()`, etc. —
   which means the ported endpoint automatically gains everything built into `/chart` this
   session that `astro-engine-v2` predates: Dasha (`core/dasha_tree.py`), rise/set
   (`core/riseset.py`), the dual birth-moment/sunrise Panchang split, input validation, and
   high-latitude graceful degradation. None of that needs to be re-implemented for Horary —
   it's the same downstream pipeline `/chart` already has, called from a different starting
   moment.
4. **Regression test** the ported search against the self-check `horary.py` already has
   built in (the sub-lord assertion in `find_exact_ascendant_time`) — this should still pass
   post-port, and passing is itself a correctness signal for the port, not just for the
   original code.
5. **Frontend**: a horary entry form (date + location + horary number 1–249, or a "count
   beans/pick a number" UX per KP Horary tradition) reusing `BirthDataForm`'s location
   autocomplete and the existing chart-display components (`PlanetaryTable`, `CuspTable`,
   `SignificatorTable`, `RulingPlanetsStrip` all already accept the same data shape `/chart`
   returns, and `/horary`'s response — per §1.1 — is that same shape plus `horaryNumber`/
   `matchedDateTime`/`horaryZone`).

## 4. Integrating Gochara

Two integration models, genuinely different in scope — worth deciding deliberately rather
than defaulting to one:

### Option A — keep it a separate service, link to it

Gochara already runs as its own FastAPI process on its own port (`8100` in its own docs),
reusing `astro-engine`'s ephemeris files via a relative sibling-folder path. Minimal work:
run both processes, add a "Transit Timeline" link/iframe from the main
`Astro-Engine-v2.0` frontend to Gochara's UI. No code changes to either repo. Downside: two
processes to run and deploy, two ayanamsa-mode selectors a user could set inconsistently
between the natal chart and the transit view.

### Option B — fold transit sampling into the main API

Add a `POST /transit` endpoint to `astro-engine`'s `services/app.py`, porting
`Astro-Engine-Gochar/backend/ephemeris.py: sample_ephemeris()`'s logic in (already verified
accuracy-correct, §2 — this is a much smaller port than Horary's, no fix needed, just
relocation). The existing `Astro-Engine-v2.0` frontend would then need a new canvas-based
timeline view — Gochara's `frontend/app.js` is dependency-free vanilla JS/canvas, so it's a
reasonable starting point to adapt rather than a full rewrite, but it is still new frontend
work, unlike Option A.

**Recommendation: start with Option A.** It's deployable in under an hour (no code changes,
just running a second process and adding a link), ships the capability immediately, and
doesn't foreclose Option B later — porting `sample_ephemeris()` into the main API remains
just as easy to do afterward as before, once it's clear the transit feature is actually used
enough to justify unifying the two UIs.

## 5. Verification

- **Horary**: the self-check already in `find_exact_ascendant_time` (sub-lord assertion) is
  the primary regression test — it must still pass after the ayanamsa-threading changes in
  §3. Additionally, spot-check a handful of horary numbers (e.g. 1, 125, 249 — first, middle,
  last table rows) against `research/PyJHora`'s or `research/VedicAstro`'s own horary/prasna
  chart construction for the same date/location/number, the same cross-verification pattern
  used throughout this plan folder.
- **Gochara**: since §2 already confirmed its ayanamsa/longitude math independently matches
  the fixed pattern, no arcsecond-level re-verification is needed. What's worth checking
  post-integration: that it's actually pointed at the *current* `astro-engine/ephemeris`
  path (a relative sibling-folder assumption, per §1.2 — will silently fall back to lower-
  precision Moshier if the folder layout doesn't match what Gochara's `backend/main.py`
  expects, without erroring, so this is a "did it silently degrade" check, not a crash to
  watch for).

## 6. Why this plan is different from Plans 4 and 5

Plans 4 and 5 are new calculation work — every rule table in Plan 4 beyond D9, and every
Muhurta table in Plan 5 beyond Hora, still needs to be sourced and verified from scratch, and
this round's own drafting process demonstrated (twice) how easy it is to get that wrong from
memory. Both features in this plan are the opposite situation: the hard part (the actual
astronomy and the classical rule tables) is already written, already tested, and in Horary's
case already cross-validated against two independent external references by whoever built
`astro-engine-v2`. What's missing is integration effort — porting code through this session's
accuracy fix (§3) and a deployment decision (§4) — not new domain research. That makes this
the highest-confidence, fastest-to-ship plan of the three, and a reasonable candidate to
implement before Plans 4/5's still-unresolved table-sourcing work, despite being written last.
